# `haetdeul.ml_price_forecasts` 컬럼 정의서 v1

**ML 파트가 만든 가격 예측을 매입 파트에 넘기는 표입니다.**

작성 2026-08-27 · 대상 DB `test` (<DB호스트>) · 스키마 `haetdeul`

---

## 이 표가 뭔가

우리가 예측한 가격을 매일 여기에 넣습니다. 매입 파트 프로그램이 이걸 읽어
매입 판단에 씁니다.

```
우리 창고(cost_catcher_raw)  →  예측  →  여기(test/haetdeul)  →  매입 파트가 읽음
```

**1줄 = 기준일 하나 × 품목 하나 × 가격종류 하나 × 며칠 뒤 하나**

기준일 하루에 **162줄**이 들어갑니다 (가격 3종 × 품목 3개 × 18일).

---

## 꼭 알아야 할 세 가지

### 1. 날짜는 달력 날짜입니다

`offset_days` 는 **그냥 며칠 뒤**입니다. 1이면 내일, 18이면 18일 뒤입니다.

우리 내부에서는 **장이 서는 날만** 셉니다(토·일·공휴일 건너뜀). 하지만 매입
파트 프로그램은 달력 날짜를 쓰므로, 넣을 때 **우리가 달력 날짜로 바꿔서**
넣습니다.

`target_dt = base_dt + offset_days` 가 항상 성립합니다. 표가 이걸 강제합니다.

### 2. 장이 안 서는 날은 채워 넣은 값입니다

토요일·일요일에는 경매가 없어서 예측이 없습니다. 그런 칸은 **가장 가까운
장날 예측**을 넣고 `is_filled = TRUE` 로 표시합니다.

**이 표시를 꼭 확인하세요.** 18일 중 5~7일이 채운 값입니다.

> **★ 2026-08-31 수정 — 앞쪽 빈칸도 이제 채웁니다.**
>
> 예전에는 **기준일 다음날이 장이 안 서는 날이면 그 칸을 통째로 빼고**
> 있었습니다. 그래서 기준일마다 줄 수가 달랐습니다.
>
> ```
> 기준일 8/27(목) → 다음 장날 8/28(금)  = D+1 부터   18줄
> 기준일 8/28(금) → 다음 장날 8/31(월)  = D+3 부터   16줄  ← 앞 2칸이 없었음
> 기준일 12/31(수) → 다음 장날 1/2(금)  = D+2 부터   17줄  ← 1/1 신정
> ```
>
> **금요일마다, 그리고 공휴일 앞에서 나던 일입니다.** 8/28 만의 예외가
> 아니었습니다. 첫 줄이 D+1 이라고 믿고 자리로 세면 14번째가 2주 뒤가
> 아니라 16일 뒤가 됩니다.
>
> 이제는 앞쪽 빈칸도 가장 가까운 예측으로 채워 **항상 D+1~D+18 이 18줄
> 전부** 나옵니다. 이때도 `is_filled = TRUE` 입니다.
>
> **그래도 자리(순서)로 세지 마세요.** `offset_days` 나 `target_dt` 를
> 읽으세요. 우리가 또 실수하면 자리로 세는 코드는 조용히 틀린 답을 냅니다.

### 3. 값이 무엇을 가리키는지 함께 넣습니다

경락가는 **포장 규격에 따라 가격이 크게 다릅니다.** 같은 배추 특등급이라도
10kg 그물망은 710.8원/kg, 1kg 소포장은 11,223.7원/kg 입니다.
**우리가 넘기는 값은 그물망+파렛트 10kg 를 물량가중으로 합친 721.9원입니다.**

그래서 **어떤 규격을 예측한 것인지**를 `spec_desc` 에 같이 넣습니다.

## 컬럼

### 키 — 이 넷이 한 줄을 구분합니다

| 컬럼 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `base_dt` | 날짜 | ✅ | **예측한 날.** 이 날까지의 정보만 써서 예측했습니다 |
| `item_nm` | 글자 | ✅ | `배추` · `무` · `양파` |
| `target_kind` | 글자 | ✅ | `AUC` 경락가 · `WHSL` 중도매가 · `RTL` 소매가 |
| `offset_days` | 정수 | ✅ | **며칠 뒤.** 1~18 |

기본키 = (`base_dt`, `item_nm`, `target_kind`, `offset_days`)

### 예측값 — 매입 파트가 실제로 쓰는 값

| 컬럼 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `target_dt` | 날짜 | ✅ | 예측 대상 날짜. `base_dt + offset_days` |
| `predicted` | 정수 | ✅ | **예측 가격** |
| `lower` | 정수 | ✅ | **하한.** 이보다 낮을 가능성은 10% |
| `upper` | 정수 | ✅ | **상한.** 이보다 높을 가능성은 10% |
| `current_price` | 정수 | ✅ | **★ 실제 거래가가 아닙니다.** 모델의 출발점. 아래를 꼭 읽으세요 |
| `unit` | 글자 | ✅ | `원/kg` (소매는 품목별로 다름) |

**하한~상한 사이에 10번 중 8번이 들어옵니다.** 나머지 2번은 벗어납니다.

⚠ **범위가 넓습니다.** 배추 경락가 예로 `예측 610원 · 하한 395 · 상한 831` 입니다.
이건 실제 오차가 그만큼 크기 때문입니다. 좁게 주면 거짓말이 됩니다.

---

### ★ `current_price` — **실제 거래가가 아닙니다. 모델의 출발점입니다**

> **⚠ 2026-08-31 정정.** 같은 날 아침에 이 자리에 "진짜 거래된 가격" 이라고
> 적었습니다. **틀렸습니다.** 매입 파트가 산식을 재현하려다 안 맞아
> 물어보셔서 드러났습니다. 그 설명을 보고 작업하셨다면 버려 주세요.

**두 값을 섞은 것입니다.**

```
current_price = α × 어제값  +  (1 − α) × 최근 7일평균
```

| `target_kind` | α | 뜻 |
|---|---|---|
| `AUC` 경락가 | **0.4** | 어제값 40% + 7일평균 60% |
| `WHSL` 중도매가 | **0.8** | 어제값 80% + 7일평균 20% |
| `RTL` 소매가 | **1.0** | 어제값 그대로 (섞지 않음) |

기준일 2025-12-31 배추 경락가를 분해하면 이렇습니다.

```
0.4 × 824.0(12-30 실측)  +  0.6 × 803.6(7일평균)  =  811.8  →  전달표 812
```

**왜 섞나.** 어제 하루 값만 쓰면 그날 우연히 튄 값에 예측 전체가 끌려갑니다.
7일평균을 섞으면 그게 줄어듭니다. 섞는 비율(α)은 타겟마다 실험으로 정했고,
소매가는 안 섞는 게 제일 좋아서 α=1.0 입니다.

**두 가지를 더 알아두세요.**

**① 날짜는 "기준일 이전" 최신 경매일입니다. 당일이 아닙니다.**
배치가 아침 9시에 도는데 그날 경매가 아직 안 끝났기 때문입니다.
`base_dt = 2025-12-31` 이면 **12-30** 값을 씁니다 (824.0).
12-31 당일 값은 933.0 이지만 예측 시점에는 모르는 값입니다.

**② 7일평균은 날짜별로 물량을 다시 가중하지 않습니다.**
하루 단위로 물량가중가를 만든 뒤, 그 7개를 **단순평균**합니다.
"후행 7영업일 전체 물량가중"(819.4)과는 다른 값입니다.

### 그래서 — **매입 단가로 쓰지 마세요**

```
current_price   모델이 출발점으로 삼은 값 (섞은 값 · 이전 영업일 기준)
매입 단가        실제로 그 가격에 살 수 있는 값
```

**둘은 다른 시리즈입니다.** 매입 판단에 쓰시려면 산출물에 그 사실을
고지하셔야 합니다.

섞지 않은 실측값이 필요하시면 **`latest_actual_price` · `latest_actual_dt`
컬럼을 추가로 드리겠습니다** (협의 중 · 2026-08-31).

**`current_price` 는 baseline 이기도 합니다.** 우리 모델이 이 값을 못 이기면
모델을 쓸 이유가 없습니다. 그래서 `use_recommended = FALSE` 인 조합은
`predicted` 가 사실상 이 값과 같게 나갑니다.

> **`target_kind` 를 맞춰서 쓰세요.** 같은 배추라도 단계마다 값이 두세 배
> 다릅니다. 2026년 1월 실제 평균은 경락가 817원 · 중도매가 1,201원 ·
> 소매가 4,867원이었습니다.

### 값의 정체 — 무엇을 예측한 것인가

| 컬럼 | 형식 | 설명 |
|---|---|---|
| `market_name` | 글자 | `서울가락` |
| `grade_name` | 글자 | `특` |
| `spec_desc` | 글자 | `그물망·파렛트 10kg` 같은 규격 설명 |
| `unit_weight_kg` | 숫자 | `10` · `20` · `15` |

**규격 기준 (2026-08-27 확정)**

| 품목 | 포장 | 무게 |
|---|---|---|
| 배추 | 그물망 · 파렛트 | 10kg |
| 무 | 상자 · 파렛트 | 20kg (2018년 이전은 18kg) |
| 양파 | 그물망 · 파렛트 | 15kg |

소포장(8kg 이하)과 트럭 단위는 뺐습니다. 다른 상품이기 때문입니다.

**등급을 `상` 이 아니라 `특` 으로 한 이유**: 가락시장 물량의 98%가 특등급입니다.
양파는 상 등급이 1년에 30~54일만 거래돼 매일 값을 만들 수 없습니다.

## 표가 스스로 막는 것

잘못된 값이 들어가지 못하게 표에 규칙을 걸어뒀습니다.

| 규칙 | 무엇을 막나 |
|---|---|
| `target_dt = base_dt + offset_days` | **날짜 계산을 틀리게 넣는 것.** 우리 내부 기준(장 서는 날)이 실수로 섞이면 저장이 거부됩니다 |
| `lower ≤ predicted ≤ upper` | 하한이 상한보다 큰 값 |
| `predicted > 0` | 0원이나 음수 |
| `offset_days` 는 1~18 | 범위 밖 |
| `target_kind` 는 AUC/WHSL/RTL | 오타 |
| `generated_at` 날짜 ≤ `base_dt` | **미래 정보로 과거를 예측한 것처럼 꾸미는 것** |

마지막 규칙이 중요합니다. 예측을 만든 시각이 기준일보다 나중이면 저장이
거부됩니다. 성적을 부풀리는 실수를 표가 막습니다.

## 읽는 방법

### 그냥 읽기

```sql
SELECT target_dt, predicted, lower, upper, is_filled
  FROM haetdeul.ml_price_forecasts
 WHERE base_dt = '2026-08-26'
   AND item_nm = '배추' AND target_kind = 'AUC'
 ORDER BY offset_days;
```

### 프로그램이 쓰기 좋은 모양으로

`haetdeul.v_ml_price_forecast` 라는 **미리 만들어 둔 조회**가 있습니다.
18일치를 하나로 묶어 줍니다.

```sql
SELECT * FROM haetdeul.v_ml_price_forecast
 WHERE target_kind = 'AUC' AND item = '배추' AND as_of = '2026-08-26';
```

나오는 모양:

```json
{
  "as_of": "2026-08-26",
  "item": "배추",
  "unit": "원/kg",
  "current_price": 610,
  "horizon_days": 18,
  "generated_at": "2026-08-26T06:00:00+09:00",
  "model_version": "ops_auc",
  "has_filled_rows": true,
  "filled_count": 6,
  "daily": [
    {"date": "2026-08-27", "predicted": 610, "lower": 395, "upper": 831},
    {"date": "2026-08-28", "predicted": 610, "lower": 385, "upper": 835}
  ]
}
```

`has_filled_rows` 와 `filled_count` 로 **채운 값이 몇 개 섞였는지** 바로 알 수
있습니다.

## 우리 예측이 얼마나 맞나 (2024~2026 실측)

**꼭 보고 쓰세요.**

> **★ 2026-08-31 재측정.** 저희 채점 코드가 경락가에 규격 필터를 안 걸고
> 있어서 **34,905행 중 25,866행(74%)을 틀린 정답으로 채점**하고 있었습니다.
> 고쳐서 전부 다시 채점한 값입니다. **이전 표는 폐기하세요.**
> 여러분께 나간 예측값 자체에는 영향이 없습니다 — 틀린 것은 "얼마나
> 맞았나" 를 재던 자였습니다.

**조건**: 리드타임 3 이상 · `ops_*` 운영 모델 · 각 조합 10,197~10,361행

| 가격 | 품목 | 평균 실제가 | 평균 오차 | 평균 오차율 | 밴드 밖 |
|---|---|---|---|---|---|
| 경락가 | 배추 | 684원 | **261원** | **35.1%** | 41% |
| 경락가 | 무 | 547원 | 102원 | 21.7% | 20% |
| 경락가 | 양파 | 796원 | 130원 | 17.0% | 41% |
| 중도매가 | 배추 | 1,099원 | 91원 | 8.4% | 8% |
| 중도매가 | 무 | 832원 | 104원 | 12.7% | 17% |
| 중도매가 | 양파 | 984원 | 109원 | 11.0% | 32% |
| 소매가 | 배추 | 4,107원 | 307원 | 7.7% | 10% |
| 소매가 | 무 | 1,991원 | 156원 | 7.9% | 14% |
| 소매가 | 양파 | 1,920원 | 138원 | 7.5% | 20% |

**경락가가 가장 안 맞습니다.** 매일 경매로 새로 정해지는 값이라 많이 흔들립니다.
중도매가·소매가는 유통 단계를 거치면서 평평해져서 훨씬 잘 맞습니다.

**배추 경락가가 제일 나쁩니다 (35.1%).** 1,000원짜리를 351원 틀립니다.

매입 파트 프로그램이 **"예측 오차 8% 이내"를 전제**로 만들어져 있다면
**그 전제는 경락가에서 성립하지 않습니다.** 소매가는 7.5~7.9% 로 겨우
맞지만, 경락가는 17~35% 입니다. 이건 모델이 나빠서가 아니라 농산물
경매가가 원래 그만큼 흔들리기 때문입니다.

**밴드(하한~상한) 기준으로는** 경락가 배추·양파가 10번 중 4번 벗어납니다.
"10번 중 8번" 목표를 못 지키고 있는 조합입니다. 저희가 개선해야 할 부분이고,
그때까지는 이 표를 보고 쓰셔야 합니다.
