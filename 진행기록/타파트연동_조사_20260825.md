### 팀 작업 방식 — tests·mock 이 먼저다

**커밋 로그로 판정하면 틀립니다.** 세어보면 "app만 24 · app+test 동시 23 ·
test만 5 · 테스트가 앞선 커밋 0" 이라 TDD 가 아닌 것처럼 보입니다.

사용자가 팀에 직접 확인한 결과 **tests·mock 에서 먼저 구현하고 app 에 적용**하는
방식이었습니다. 로컬에서 테스트를 먼저 쓰고 통과시킨 뒤 한 커밋으로 올리기 때문에
커밋 안쪽이 안 보였던 것입니다. `mocks/README.md` 가 뒷받침합니다.

> "장식용 샘플이 아니라 **노드 단위 테스트 4종의 입력**이다 (CLAUDE.md '작업 방식')"

**그래서 우리 인계 형태가 달라집니다.** 문서로 "우리 출력은 이렇습니다"가 아니라
**그쪽 테스트를 통과하는 mock 형태**로 넘겨야 그 방식에 맞습니다.

## 3. 불일치 4건 (실측)

### ① 예측 구간 폭 — 설계 변경이 필요할 수 있음 ★

`constraints.yaml` 이 **`ci_width = (upper−lower)/predicted ≥ 0.08` → "불확실"** 로
분류하고, 그러면 공격안(선매입·타이밍 축)이 사라집니다. 판정 기준일은 D+14.

| 품목 | 우리 ci_width (LT14) | mock | 임계 |
|---|---|---|---|
| 배추 | **0.73** | 0.03~0.12 | 0.08 |
| 무 | **0.65** | | 0.08 |
| 양파 | **0.40** | | 0.08 |

**먼저 "우리 구간이 과대한가"를 의심하고 실제 오차를 따로 쟀습니다.**

```
D+14 절대오차   평균  배추 21.1% · 무 24.0% · 양파 18.1%
                80분위 배추 27.6% · 무 34.2% · 양파 28.2%
```

**구간이 부풀려진 게 아니라 실제 오차가 그만큼입니다.** `0.08` 은 오차 ±4% 를
전제한 값이고 2주 앞 경락가에서는 도달할 수 없습니다. mock 이 0.03~0.12 를 쓰고
있어 그 범위로 임계가 정해진 것으로 보입니다.

그대로 연결하면 **첫날부터 모든 날이 `uncertain` 이 되어 공격안이 영원히 안 나옵니다.**

추가로 mock 은 `ci_width` 를 18일 내내 **일정하게** 유지하는데(README 가 의도를
밝힘 — 판정일만 맞추면 기준일이 바뀔 때 조용히 뒤집히므로), 우리 실측은
**LT1 0.42 → LT18 0.83 으로 두 배 벌어집니다.** 상황 분류를 D+14 한 점으로 하는
설계가 실데이터에서 어떻게 동작할지 함께 봐야 합니다.

### ② 날짜 축 — 영업일 vs 달력일

계약은 **연속 달력일 D+1~D+18** 이고 코드가 `daily[13]` 을 D+14 로 인덱스 접근합니다.
테스트 이름에도 `..._is_the_fourteenth_calendar_day` 로 박혀 있어 해석의 여지가 없습니다.

우리 `lead_biz_d` 는 **영업일**(조사 축)이라 중간이 빕니다.

```
지평:  우리 LT1~18 = 24~26 달력일  →  18일 지평은 부족이 아니라 잉여
빈칸:  18일 창에서 4일 (토 2 · 일 2)
```

### ③ D+14 판정일이 10.8% 확률로 빈다

`14 = 2×7` 이라 기준일과 같은 요일이고 기준일은 항상 평일이므로 **주말에는
떨어지지 않습니다**(157건 중 0건). 그러나 **공휴일에는 157건 중 17건**에서
예측이 없었습니다(설날·근로자의날·어린이날·부처님오신날·지방선거일 등).

그중 다수가 `is_open = TRUE` — **경매는 열리는데 조사를 안 하는 날**입니다.

### ④ 품목 — 피마늘

계약은 배추·무·양파·**피마늘** 4종. 우리는 마늘 제외 중입니다
(경락가 결측 11% · 피/깐 구분 미확정 · 중도매가가 94%의 날에 전일과 동일).
나머지 셋은 지금 바로 가능합니다.

## 5. 설계 결정

**날짜 축 변환은 우리가 맡습니다.** 휴장 달력(`ref_calendar`)을 우리가 관리하므로,
변환을 그쪽 포트에 넣으면 우리 도메인 지식이 남의 코드에 복제됩니다.

**표에 제약으로 못 박았습니다.**

```sql
CHECK (target_dt = base_dt + offset_days)   -- 영업일 축이 섞이면 적재 실패
CHECK (lower <= predicted AND predicted <= upper)
CHECK ((generated_at AT TIME ZONE 'Asia/Seoul')::date <= base_dt)  -- look-ahead 방어
```

테스트가 잡기 전에 DB 가 먼저 막습니다.

**채운 값을 숨기지 않습니다.** `is_filled` · `src_lead_biz_d` 를 함께 싣습니다.
채운 값과 진짜 예측이 구분되지 않으면 그쪽 문서가 반복해서 경계하는
"조용히 통과"가 그대로 재현됩니다.

**계약에 없는 것도 싣습니다.** `is_gated`(LT<3 앵커 대체) · `gate_reason`.
포트가 무시해도 되지만 문제가 났을 때 "이 값이 어디서 왔나"를 되짚을 유일한 통로입니다.

### 신뢰도 신호를 계약에 실을 것 (제안)

지금 계약에는 **품목별 신뢰도를 전달할 필드가 없습니다.**

```
auc  양파   검증 −0.1% · 테스트 −6.2%   →  X  차단 유지
whsl 무     검증 +17.3% · 테스트 −13.2%  →  X  차단 유지
```

**양파 경락가는 우리 모델이 baseline 보다 나쁩니다.** 그런데 구매 Agent 는 배추
예측과 양파 예측을 같은 신뢰도로 씁니다. `ref_prediction_quality` 에 이미 있는
값이라 실어 보내기만 하면 됩니다 — LLM 이 낄 자리가 아니라 SQL 조건문입니다.
