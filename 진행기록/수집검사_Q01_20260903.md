## 1. 왜 재생성 앞인가

`DBEAVER_run_v5.sql` 은 **맨 앞에서 TRUNCATE** 합니다.

```
수집 -> [여기서 검사] -> 재생성(TRUNCATE) -> 추론 -> 적재 -> 매입 파트
```

수집이 이상한 자료를 가져오면 **멀쩡한 학습표를 지우고 이상한 걸 채웁니다.**
**여기가 마지막으로 되돌릴 수 있는 자리**입니다.

### `quality_agent` 와 무엇이 다른가

```
quality_agent   배치가 끝난 뒤 · 타겟의 뜻이 맞나 (등급 순서 · 계열 건전성)
ingest_agent    재생성 앞 · 들어온 자료가 평소 같나 (행수 · 결측 · 단위)
```

**앞의 것은 "우리가 만든 값이 말이 되나", 뒤의 것은 "원천이 평소 같나"**
입니다. 08-27 규격 사고는 앞의 것이 잡을 일이었고, **수집기가 조용히
망가지는 것은 뒤의 것이라야 잡습니다.**

```

```

### ★ 원인 둘, 둘 다 고쳤습니다 (2026-09-03 17:49)

**처음에 "8월 25일 수정 탓" 이라고 적었는데 증명 못 합니다 — 정정합니다.**
git 이력이 2026-09-02 부터라 그 전을 못 봅니다. 대신 코드를 직접 읽어
원인 **둘**을 찾았습니다.

**① 기본 품목이 셋뿐이었습니다.**

```python
ap.add_argument("--items", nargs="+", default=["배추", "양파", "무"])
```

**그리고 배치는 인자 없이 부릅니다.** 나머지 셋은 아무도 요청하지 않았습니다.
*"수집기 설정에 여섯 품목이 그대로 있다"* 고 위에 적었던 것이 틀렸습니다 —
`ITEMS` 표에는 여섯이 있지만 **기본값이 셋**이었습니다.

**② 최신일을 여섯 품목의 MAX 로 뭉쳐 봤습니다.**

```python
cur.execute("SELECT MAX(exmn_ymd) FROM veg_daily_price_raw WHERE item_cd = ANY(%s)", (codes,))
```

**배추가 최신이면 `db_max` 가 최신이 되고, 뒤처진 품목의 빈 구간을
아무도 요청하지 않습니다.** ①을 고쳐 여섯으로 되돌리면 **이게 바로
물립니다** — 되돌린 순간 셋은 영영 08-24 에 머뭅니다.

**③-2 검사가 놓쳤던 것과 같은 함정입니다.** 한 품목만 살아 있으면
표 전체가 멀쩡해 보입니다. **검사도 수집기도 같은 실수를 했습니다.**

**둘 다 고쳤고 929행이 채워졌습니다** (건고추 313 · 피마늘 63 · 깐마늘 553).
여섯 품목 다 **2026-09-02** 까지 최신이고 검사가 통과합니다(종료코드 0).
품목별 최신일을 매번 찍고, 다른 품목보다 3일 넘게 뒤처지면 `★` 를 답니다.

## 3. ★★ 이 검사를 만들면서 제가 세 번 틀렸습니다

**전부 오늘 다른 데서 배운 것과 같은 함정이었습니다.**

### ① 검사 하나가 죽으면 나머지가 조용히 다 죽었습니다

```
check_lag 실패 (컬럼명 오류)
  -> PostgreSQL 이 그 트랜잭션의 뒤 쿼리를 전부 거부
  -> 나머지 네 검사가 다 죽음
  -> 그런데 "중복 정상" 이라고 찍힘
```

**롤백을 안 해서였습니다.** 오늘 아침 그림자 실행이 자기 자신과 비교하면서
계속 "성공" 으로 찍히던 것과 **같은 종류**입니다.

### ② 자연키를 확인 없이 적어 오탐이 1,068 + 1,323 건 났습니다

```
경락가에서 subclass_code 를 빠뜨림   -> 1,068건 오탐
소매가에서 mrkt_cd(점포) 를 빠뜨림    -> 1,323건 오탐
```

소매 조사는 같은 날·같은 품목을 **여러 점포**에서 잽니다(경동·복조리·B유통…).
그게 정상입니다. 경락가는 같은 규격 안에서도 **소분류**가 갈립니다 —
**오늘 아침에 제가 직접 확인한 것인데 검사를 짤 때 잊었습니다.**

> **잘못된 경보가 매일 뜨면 사람이 진짜 경보도 무시하게 됩니다.**

### ③ 표 전체 최신일만 봐서 "정상" 이라고 찍었습니다

**세 품목이 10일 멈춰 있는데 `check_lag` 는 "정상" 이었습니다.**
표 전체 최신일이 배추 때문에 09-02 였기 때문입니다.

**한 품목만 살아 있어도 표 전체는 멀쩡해 보입니다.**
품목별 검사(`check_item_lag`)를 따로 만들어 잡았습니다.

> **오늘 매입 파트와 주고받은 그 이야기입니다** — "검사가 돌았나" 가
> 아니라 **"검사가 실제로 무엇을 봤나"**. 검사를 만들면서 제가 그 함정에
> 세 번 빠졌습니다.

## 5. 검사 여섯

```
①   수집 지연      원천마다 최신일이 며칠 밀렸나
①-2 품목별 지연    ★ 표 전체가 멀쩡해도 한 품목만 멈출 수 있다
②   행수 급감      최근 30일 중앙값의 몇 %인가
③   중복          같은 자연키가 두 번 들어왔나
④   단위 변화      가격 수준이 갑자기 몇 배로 뛰었나 (원/kg <-> 원/포)
⑤   결측률 급증    그 컬럼의 평소와 견줘 얼마나 늘었나
```

### ★ 고정 문턱을 안 씁니다

백로그가 짚은 대로 **정상 결측과 사고성 결측이 다릅니다.**

```
sumRn 결측 57.7%           정상 (비가 안 오면 빈다)
prod_area_temp 0% -> 30%   사고
```

**최근 이력을 기준선으로 삼고 거기서 얼마나 벗어났나**를 봅니다.
문턱을 손으로 적으면 *"62.2% 는 괜찮다"* 같은 예외 목록이 끝없이 늘어납니다.

### 아무것도 못 본 검사를 스스로 신고합니다

근거 수치가 하나도 없는데 "정상" 인 검사가 있으면 **그것 자체를 주의로
올립니다.** *"정상이라서가 아니라 볼 자료가 없어서일 수 있습니다."*
