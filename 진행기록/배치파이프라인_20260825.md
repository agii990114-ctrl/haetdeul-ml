## 설계에서 신경 쓴 것

### ① 실패하면 거기서 멈춘다

반쯤 돌린 상태로 예측을 내보내지 않습니다. 다만 **수집 단계는 예외**입니다 —
5종이 서로 독립이라 하나가 실패해도 나머지는 돌립니다. 모두 멈추려면 `--strict`.

### ② 신선도 가드는 조사일 기준으로 잰다 ★

앵커가 낡았는데 추론하면 **몇 달 전 가격으로 "오늘의 예측" 을 내놓게 됩니다.**
예외가 아니라 그럴듯한 숫자로 나오므로 가장 위험한 사고입니다.

**달력일로 재면 안 됩니다.** 오늘(8/25) 기준 마지막 조사일이 8/21 이라 달력일로는
4일이지만, 그 사이 주말이 껴서 실제로 놓친 조사일은 **2일**뿐입니다. 달력일로
임계를 걸면 주말·연휴마다 오탐이 납니다.

```sql
SELECT COUNT(*) FROM ref_calendar
WHERE is_survey AND dt > (앵커 최신일) AND dt <= CURRENT_DATE
```

임계(기본 3)를 넘으면 **추론 자체를 안 하고 중단**합니다. 확인 결과, 임계를 1로
낮추면 predict 에서 멈추고 load·score 가 아예 실행되지 않습니다.
정말 필요하면 `--force-stale`.

### ③ v5 는 트랜잭션 안에서 돌린다

`DBEAVER_run_v5.sql` 은 맨 앞에서 `TRUNCATE` 합니다. 중간에 실패하면 학습
테이블이 빈 채로 남습니다. 배치는 트랜잭션으로 감싸 **성공했을 때만 커밋**하고,
실패하면 롤백해 이전 상태를 지킵니다.

### ④ 학습은 배치에 없다

매일은 **추론만** 합니다. 학습은 월 1회 또는 드리프트 감지 시 사람이 돌립니다.
매일 학습하면 예측이 요동쳐 "왜 어제와 다르냐" 에 답할 수 없습니다.

### ⑤ 수집 기간을 DB 에서 정한다

기상은 `weather_asos_raw` 최신일 다음 날부터, 반입량은 최신일 −5일부터
(8일 창이 겹치도록) 자동으로 잡습니다. 날짜를 하드코딩하지 않습니다 —
오늘 v5 에서 `'2025-12-31'` 하드코딩 때문에 8개월치가 조용히 버려진 일이 있었습니다.

## 단계

| 단계 | 하는 일 | 소요 |
|---|---|---|
| `collect_auction` | `auction_collector update --load-postgres` | ~1분 |
| `collect_price` | `collect_kamis.py` (증분 + 적재) | ~1분 |
| `collect_weather` | `fetch_asos.py --load-db --no-csv` | 지점 95개 |
| `collect_volume` | 농넷 스크래핑 → `merge --load-db --no-csv` | **~40초** (증분) |
| `collect_econ` | `fetch_economic_variables.py --load-db --no-csv` | ~1분 |
| `rebuild` | v5 (crop_price_train + predict_input) | ~80초 |
| `predict` | `export_predict_input.py` → `predict.py` × 3 | ~10초 |
| `load` | `load_predictions.py` | ~1초 |
| `score` | `score_predictions.py` | ~1초 |

**반입량은 매일 돌려도 40초입니다.** 처음에 "20~25분" 으로 적었던 건 8개월치
백필 기준이었습니다. 배치는 DB 최신일 −5일부터만 받으므로 8일 창 하나(5품목 ×
5회 호출)면 끝납니다. 건너뛸 이유가 없습니다.

### 반입량은 정정된다 ★

농넷은 **수급일보**라 최근 물량이 뒤늦게 반영됩니다. 실측(2026-08-25)에서
8/18~8/24 17건이 전부 늘었습니다.

```
2026-08-18 양파   1,407 → 1,658톤
2026-08-20 무       677 →   700톤
2026-08-21 양파     618 →   662톤
```

`DO NOTHING` 이면 이 정정이 반영되지 않아 **모델이 낡은 물량으로 학습**합니다.
그렇다고 전 구간을 덮어쓰면 스크래퍼가 깨졌을 때 이상한 값이 그대로 들어갑니다.

**최근 14일만 덮어쓰고 그 이전은 건드리지 않습니다.** 정정은 며칠 안에서만
일어나므로, 오래된 값이 갑자기 바뀌면 그건 정정이 아니라 사고입니다.

무엇이 달라졌는지 로그에 남깁니다 — 건수만 찍으면 매번 손으로 캐야 합니다.

## CSV 를 파이프라인에서 뺐다 (같은 날 오후)

원래 기상·반입량·경제는 **수집 → CSV → 로더 → DB** 였습니다. 지금은 수집기가
바로 넣습니다.

```bash
python fetch_asos.py 20260820 20260822 --load-db --no-csv
python "농넷에서 일일산출량 적재.py" run --start ... --load-db --no-csv
python fetch_economic_variables.py --start-date ... --load-db --no-csv
```

**CSV 가 타입을 지우기 때문입니다.**

```
빈 문자열 → NULL      기상 sumRn (무강수일). 0 과 결측은 다르다
"1718.0"  → int       반입량 total_ton
```

복원 규칙이 로더에 따로 살아 있었고, 한 글자만 틀려도 조용히 틀립니다.
파이썬에서 바로 넣으면 `None` 은 `None`, `int` 는 `int` 입니다.
인코딩(utf-8-sig · cp949) 문제도 사라집니다.

**검증은 그대로 옮겼습니다.** 기상의 계약 점검 7종 중 파일이라서 되는 둘
(인코딩·BOM)만 빠지고 나머지 다섯은 `verify_rows()` 로 메모리에서 돕니다.
겹치는 구간 값 대조도 공용 모듈(`데이터 수집/_dbload.py`)에 모아 셋이 같은
방식으로 잽니다.

**남긴 CSV 는 이유가 있는 것뿐입니다.**

| 파일 | 왜 남기나 |
|---|---|
| 반입량 `raw.jsonl` | 25분 스크래핑 이어받기 (`_done.txt` 와 짝) |
| 경락가 CSV·Excel·ZIP | 팀 배포 산출물. 파이프라인이 아니라 제품 요구 |

기존 `load_to_pg.py` · `load_daily_volume.py` 도 지우지 않았습니다 —
이미 받아둔 CSV 를 넣거나 과거분을 복구할 때 씁니다.
