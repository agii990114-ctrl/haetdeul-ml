## 3. 달력이 두 개였다

`ref_calendar` v1 은 축이 하나였고 **경매 거래일**로 검증돼 있었습니다.
그런데 `lead_biz_d` 는 **중도매가 조사일** 축입니다.

```
가락 경매 거래일   2015~2025   3,348일
중도매가 조사일                2,700일
```

648일 차이의 내역입니다.

| 차이 | 건수 | 성격 |
|---|---|---|
| 토요일 | 544 | 경매는 열지만 KAMIS 조사는 안 한다 (조사일 중 토요일 **0건**) |
| 공휴일 | 약 124 | 경매는 열지만 조사는 안 한다 |
| 12월 첫째 금요일 | 11 | 시장 자체 휴장. **11년 연속** |
| 역방향 | 16 | 신정 1/2 등 — 경매는 휴장인데 조사는 한다 |

명절도 하루씩 어긋납니다.

```
경매      D-1 거래  │ D0  D+1 D+2 휴장
중도매 조사  D-1 휴무 │ D0  D+1 휴무      ← 법정 연휴 그대로
           (실측 D-1 미조사 17/17 · D0 16/16 · D+1 14/14, 예외 0건)
```

v1 축을 그대로 `lead_biz_d` 에 연결했다면 축이 24% 늘어 모든 `target_dt` 가
이동하고, 토요일·공휴일 대상일에는 중도매가가 없어 타겟이 대량 NULL 이 됩니다.

### 공휴일 소스 — KASI 특일 정보 API

```
SpcdeInfoService / getRestDeInfo(solYear, solMonth)
locdate · dateKind · isHoliday · dateName
REST · JSON · 30 TPS · 갱신 연 1회
```

2015~2028 공휴일 264건을 API 호출 14회로 수집했습니다.
수집기는 `데이터 수집/휴일 달력/fetch_holidays.py` 입니다.

**API 에 없는 휴무가 두 종류** 있습니다.

- **5/1 근로자의 날** — 법정공휴일이 아니라 근로자의 날 제정에 관한 법률에
  따른 유급휴일이라 API 가 주지 않습니다. 그런데 KAMIS 조사는 쉽니다 (8건)
- **12월 첫째 금요일** — 시장 자체 휴장 (11건)

그리고 2015-08-14(광복 70주년 임시공휴일)은 API 에 소급 등록돼 있지 않아
override 1건으로 처리했습니다.

### 확정 규칙 — 실측 2,700일 완전 일치

```
조사 축 휴무 = 토·일 + ref_holiday + 5/1 + 12월 첫째 금요일 + override
경매 축 휴장 = 일 + 신정 1/1~1/2 + 명절 당일~+2일 + 8월 첫 토요일 + override
```

| 검사 | 결과 |
|---|---|
| 축별 일수 (2015~2025) | 경매 3,348 · 조사 2,700 — 실측 일치 |
| 경매 축 vs 실거래일 | 오탐 0 · 미탐 0 (2016-01 ~ 2026-08) |
| 조사 축 vs 실조사일 | 오탐 0 · 미탐 0 |
| `lead_biz_d` 재현 | 배추·양파·무 **불일치 0** / 마늘 684 |

### API 가 찾아낸 오류 — 2028 설날

명절 날짜를 하드코딩에서 `ref_holiday` 유도로 바꾸면서 대조한 결과입니다.

| 연도 | v1 하드코딩 | API 실제 | |
|---|---|---|---|
| 2015~2027 | | | 14개 연도 일치 |
| **2028 설날** | `2028-01-26` | **`2028-01-27`** | 하루 어긋남 |

연휴 01-26(수)~01-28(금) 중 가운데가 당일입니다. 하드코딩 값은 D-1 이었습니다.
경매 휴장 규칙이 "당일~+2일" 이라 이 하루가 밀리면 휴장 구간이 통째로 어긋납니다.
학습 데이터는 2025년까지라 성능에는 영향이 없고, **운영 배치에서만 터질 오류**였습니다.

이제 `ROW_NUMBER() ... WHERE rn = 2` 로 유도하므로 구조적으로 재발할 수 없습니다.

### 한계

- API 는 **현재연도 +2년**까지만 확정합니다 (2028). 매년 갱신 배치 필요
- **임시공휴일·대체공휴일은 사후 반영**입니다. 즉 예측 시점에 알 수 없는 휴일이

**같은 데이터를 순서만 바꿔 넣으면 결과가 달라집니다.**

| 행 순서 | seed 42 | seed 43 |

| CSV 그대로 | 0.1394 | 0.1389 |
| 자연키 정렬 | 0.1381 | 0.1365 |

폭이 시드 표준편차(0.0007~0.0013)와 맞먹어 **기록된 수치를 재현할 수 없었습니다.**

### 조치

`train.py` 의 `load()` 에서 자연키로 정렬합니다.
`ablation.py` · `learning_curve.py` 도 이 함수를 쓰므로 함께 적용됩니다.

```python
df = df.sort_values(["base_dt", "item_nm", "lead_biz_d"],
                    kind="mergesort").reset_index(drop=True)
```

확인: 서로 다른 두 스냅샷(`...1116`, `...1210`)이 시드별 WMAPE까지 완전히
동일한 값을 냅니다.

```
seed 42 0.1381 · seed 43 0.1365 · seed 44 0.1367   (양쪽 동일)
```

### 기록된 수치에 대한 주의 ★

**2026-08-24 이전에 기록된 모든 수치는 비결정적 순서에서 나온 값**입니다.

## 6. 추론 파이프라인

### 모델 번들 (`train.py --save-model DIR`)

추론은 학습과 완전히 같은 조건에서 돌아야 합니다. 어긋나면 예외가 아니라
**조용히 틀린 값**이 나옵니다. 위험한 것이 둘입니다.

1. **feature 순서** — LightGBM 은 이름이 아니라 위치로 받습니다.
   한 칸 밀리면 "기온 자리에 강수량" 이 들어가고 예측은 그럴듯하게 나옵니다.
2. **categorical 수준** — pandas category 는 코드(정수)로 인코딩됩니다.
   카테고리 집합이 다르면 '배추' 가 0 이었다가 1 이 됩니다.

그래서 `meta.json` 에 feature 목록·순서·카테고리 수준을 박제하고,
`predict.py` 가 하나라도 어긋나면 멈춥니다.

### `predict.py`

- 역변환 `pred = anchor * exp(out)` 을 수행하고,
  **예측 중앙값이 앵커의 0.2~5 배를 벗어나면 즉시 중단**합니다.
  역변환 누락은 로그비율(0.049 같은 값)이 가격으로 저장되는 사고라
  자릿수로 잡을 수 있습니다.
- 리드타임 게이트(LT < 3 → 앵커)를 번들 값 그대로 적용합니다.
- 입력에 정답이 있으면 채점까지 합니다.

### 재현 확인

같은 검증 구간에서 `train.py` 와 `predict.py` 가 **완전히 같은 값**을 냅니다.

```
             모델      baseline   개선율
무         0.1581    0.1946    +18.8%
배추       0.1834    0.2181    +15.9%
양파       0.0829    0.0830     +0.2%
통합       0.1359    0.1568    +13.3%
```

### 아직 없는 것

`predict.py` 는 **입력 행이 이미 있어야** 동작합니다. 그런데 `crop_price_train`
은 타겟이 존재하는 행만 담으므로 미래 기준일 행이 없습니다.
`predict_input` 생성 SQL 이 다음 과제입니다.

## 7. `prediction_log` — 다른 파트용 계약

모델이 운영에 올라가기 전에 다른 파트가 연동을 시작할 수 있도록
테이블과 더미 데이터를 만들었습니다 (`SQL/28_prediction_log.sql`).

**값은 더미지만 구조는 실제 운영에서 쓸 것과 같습니다.**

| 대상 | 내용 |
|---|---|
| `prediction_log` | 예측 저장. 자연키 + 앵커·예측·구간·게이트·모델버전·사후채점 |
| `ref_prediction_band` | 예측 구간 근거. 품목×리드타임×타겟 실측 분위수 |
| `ref_prediction_quality` | 품목×타겟 실측 성능. `use_recommended` |
| `v_prediction_latest` | 대상일별 최신 예측 1건. `prc_to_use` 제공 |

### 예측 구간의 근거를 바꿨습니다 ★

처음에는 `pred_lo`/`pred_hi` 를 시드 편차로 만들었는데, 재보니 틀렸습니다.

```
LT3   시드 편차 1.6%   실제 WMAPE 10.4%
LT18  시드 편차 1.8%   실제 WMAPE 16.8%
```

**시드 편차는 예측 불확실성이 아닙니다.** 시드끼리 얼마나 다르게 답하느냐일
뿐이라 자릿수가 한 자리 다르고, 리드타임이 길어져도 거의 평평합니다.
그걸 신뢰구간처럼 쓰면 불확실성을 10배 가까이 과소평가합니다.

검증 구간에서 잰 `actual / pred` 비율의 q10~q90 으로 바꿨습니다.
"그 조합에서 10건 중 8건이 이 범위 안" 이라는 뜻이라 근거를 댈 수 있습니다.

| 타겟 | 밴드 폭 중앙값 | 배추 LT1 → LT18 |
|---|---|---|
| 경락가 | 59.3% | 62% → 71% |
| 중도매가 | 44.8% | 35% → 67% |
| 소매가 | 22.9% | 13% → 41% |

리드타임이 길수록 실제로 넓어집니다. `train.py` 가 학습 때 측정해 번들에
저장하고, `export_band_sql.py` 가 `ref_prediction_band` 로 내보냅니다.
모델을 재학습하면 밴드도 다시 만들어야 합니다 — 짝입니다.

> 적중률 실측 79.6% (설계 80%). 단 밴드를 잰 구간에서 측정한 값이라
> in-sample 입니다. 테스트 구간 적중률은 아직 확인하지 않았습니다.

### predict.py 출력 = 테이블 스키마

`predict.py` 가 `prediction_log` 컬럼 이름·순서 그대로 CSV 를 냅니다.
실제 예측이 그대로 적재됩니다. 컬럼 17개 일치를 확인했습니다.

더미는 난수가 아니라 **실제 앵커 가격에 결정적 변동을 얹어** 만듭니다.
재실행해도 같은 값이고 자릿수·계절성이 실제와 같습니다.

```
3-a  과거 7 기준일 (2025-11-25 ~ 12-03) · LT1~18 완전 · 1,134행
       └ 972행 채점 완료 + 162행 미채점(최신 기준일)
3-b  오늘 기준 (2026-08-24) · 대상일 08-25 ~ 09-17 · 162행
합계 1,296행
```

3-b 의 LT18 대상일이 `ref_calendar` [5] 쿼리 결과(2026-09-17)와 일치합니다.

### 소비자가 반드시 알아야 할 것 세 가지

1. **단위가 타겟마다 다릅니다.** 경락·중도매는 원/kg, 소매는 원/단위이고
   배추 소매는 포기 단위입니다. 세 값을 더하거나 비교하면 안 됩니다.
2. **모든 조합이 쓸 만하지 않습니다.** `use_recommended = false` 인 조합
   (경락 양파, 중도매 무·양파)은 모델이 baseline 보다 나쁩니다.
3. **LT1~2 는 `gated = true`** 로 나가며 `pred_prc = anchor_prc` 입니다.
   버그가 아니라 설계입니다.
