# 배치 자동 실행 등록 (Windows 작업 스케줄러) · 2026-08-25

`I-10` ①대시보드 운영 패널 · ②스케줄러 등록 완료. ③실패 알림은 미착수.

---

## 1. 등록된 작업

`taskschd.msc` → **작업 스케줄러 라이브러리 \ 원가캣쳐**

| 작업 | 주기 | 명령 | 소요 |
|---|---|---|---|
| `일별배치` | 매일 09:00 | `ops\batch.bat --skip collect_econ` | 약 6분 |
| `주간_경제지표` | 매주 월 06:00 | `ops\batch.bat --stages collect_econ` | 1초 |
| `월간_휴업공고` | 매월 1일 08:00 | `watch_garak_notice.py --future-only` | 수초 |

### 왜 경제지표를 떼어냈나

`M2` 는 두 달 늦게, `PPI`·`EPU` 는 월 단위로 갱신됩니다. 매일 받아도
같은 값이 다시 올 뿐인데 ECOS·FRED API 를 매일 두드리게 됩니다.
신선도 화면의 경제 지연 50일대는 **정상**입니다.

### 왜 휴업공고는 자동 반영이 아닌가

`watch_garak_notice.py` 는 **리포트만** 냅니다. 공고 본문이 대부분 이미지라
`alt` 속성에서 날짜를 건지는데, 정기·설 공고는 "이미지를 확인해 주세요"뿐입니다.
자동으로 돌리면 **조용히 0건을 반환하는** 가장 나쁜 형태가 됩니다.
그래서 스크립트가 추출 실패한 공고를 따로 표시하고, 사람이 보고
`ref_calendar_override` 에 넣습니다.

월 1회로 충분한 근거: 리드타임이 18영업일(3~4주)이고 비정기 휴장은 연 1.3회입니다.

| 항목 | 값 | 왜 |
|---|---|---|
| 실행 계정 | 현재 사용자 · **로그온 시에만** | "로그온 여부 무관"은 비밀번호를 스케줄러에 저장해야 합니다. `S-01`(자격증명 정리)과 정면으로 충돌해 피했습니다 |
| 놓친 작업 | **가능한 한 빨리 시작** | PC 가 꺼져 있던 날을 건너뛰면 그날 예측이 통째로 빕니다 |
| 중복 실행 | 새 인스턴스 시작 안 함 | 재생성이 `TRUNCATE` 로 시작합니다. 두 개가 겹치면 학습표가 깨집니다 |
| 실행 시간 제한 | 2시간 | 반입량 스크래핑이 초기 적재 때 20~25분입니다. 증분은 39초 |

## 3. `ops\batch.bat`

파이썬을 직접 부르지 않고 래퍼를 둔 이유가 세 가지입니다.

1. **작업 디렉터리** — 스케줄러의 "시작 위치"를 빠뜨리면 `run_batch.py` 가
   `C:\Windows\system32` 에서 `.env` 를 찾습니다. 래퍼가 `cd /d` 로 못 박습니다.
2. **로그** — 로그 없는 실패는 아무도 못 고칩니다. `ops\logs\batch_YYYYMMDD_HHMMSS.log`
   에 남기고 30일 지난 것은 지웁니다.
3. **종료 코드** — 스케줄러의 "마지막 실행 결과"가 의미를 가지려면
   `exit /b %RC%` 로 파이썬의 코드를 그대로 올려야 합니다.

경로는 ASCII(`ops\`)로 잡았습니다. 배치 파일과 스케줄러는 한글 경로에서
코드페이지 문제가 나기 쉽습니다. 로그 자체는 UTF-8 이라
`Get-Content -Encoding UTF8` 로 읽어야 안 깨집니다.

전수 대조했습니다. **공백은 `ref_calendar_override` 하나**이고, 그것도 위 3번
이유로 의도한 것입니다.

| 표 | 배치 | 비고 |
|---|---|---|
| `auction_prices_daily` · `veg_daily_price_raw` · `weather_asos_raw` · `daily_volume` | 매일 | |
| `econ_daily_raw` | 주 1회 | |
| `crop_price_train` · `predict_input` | 매일 (rebuild) | |
| `prediction_log` | 매일 (predict/load/score) | |
| `batch_run` · `batch_run_stage` | 매일 (자기 기록) | |
| `ref_calendar` · `ref_holiday` · `ref_school_day` | ✗ | **2028-12-31까지 채워져 있음**. 연 1회 갱신 |
| `ref_calendar_override` | ✗ | 2026-12-12까지. 월간 감시 작업이 후보를 냄 |
| `ref_item_station` | ✗ | 정적 매핑 17행 |
| `ref_prediction_quality` · `ref_prediction_band` | ✗ | 재학습·재평가 때만 |

**2027년 안에 달력 3종을 다시 채워야 합니다.** 지금은 859일 남았지만

## 6. 자동화 직전에 잡은 것 — 하드코딩 키 의존 ★

전체 9단계를 스케줄러 컨텍스트에서 돌려보다가 로그에서 경고 한 줄을 봤습니다.

```
[collect_price] 도·소매 증분 수집 + 적재
  성공
    [주의] 인증키를 하드코딩된 값에서 읽었습니다.
           .env 에 DATA_GO_KR_KEY 를 넣으면 이 경고가 사라집니다.
```

**매일 도는 배치가 소스 파일 안의 비밀값에 의존하고 있었습니다.**
`collect_kamis.py::service_key()` 가 키를 못 찾으면
`일별_도,소매_가격정보.py:20` 의 하드코딩 값을 정규식으로 긁어 쓰고 있었습니다.

### 원인 — 설정이 있는데도 못 읽었다

지문을 떠서 대조해 보니(값은 출력하지 않고 앞 4자 + 길이 + sha256 앞 8자만),
`데이터 수집/중도매, 소매가/.env` 의 `DATA_GO_KR_KEY` 가 **하드코딩 값과 완전히
동일**했습니다. 키가 없어서가 아니라 **`env()` 가 루트 `.env` 만 읽고 폴더 `.env` 는
안 읽어서** 폴백으로 떨어진 것이었습니다.

### 고친 것

| 대상 | 조치 |
|---|---|
| 루트 `.env` | `DATA_GO_KR_KEY` 추가 (정본) |
| `collect_kamis.py::env()` | 루트 → 폴더 순으로 읽게. `setdefault` 라 먼저 읽은 쪽이 이긴다 |
| `collect_kamis.py::service_key()` | **하드코딩 폴백 삭제.** 키가 없으면 `sys.exit` |
| `일별_도,소매_가격정보.py:20` | 하드코딩 값 제거 → 환경변수 조회 |

**폴백을 고치지 않고 없앤 이유.** 무인으로 도는 배치에서 "경고하고 계속"은 곧
"아무도 못 보는 경고"입니다. 실제로 그 경고는 계속 떠 있었지만 로그 파일 안에만
있었고, 스케줄러를 걸고 로그를 훑지 않았다면 그대로 지나갔을 것입니다.

### 검증

`--stages collect_price` 로 돌리면 "이미 최신"이라 API 호출 없이 끝나
키가 검증되지 않습니다. 좁은 구간을 강제로 받아 확인했습니다.

```
collect_kamis.py --start 2026-08-20 --end 2026-08-21 --items 배추 --check
  → 배추  113건 · 경고 없음
```

전체 `.py` 재스캔에서 남은 하드코딩 키 **0건**입니다.

## 7. 남은 것

**③ 실패 알림** — 채널 미정. 지금은 대시보드 운영 패널을 봐야 압니다.
`batch_run.status` 가 `fail`/`partial` 이거나 마지막 실행이 30시간을 넘으면
알리는 형태. 사내 메신저 웹훅이 가장 간단합니다.

**`api key/*.txt` 평문 비밀번호** — garak.co.kr 계정(id 11435·11436) 조회 URL 에
비밀번호가 평문으로 들어 있습니다. **코드는 이 값을 쓰지 않습니다**(경락가 수집기는
공공데이터포털 키 사용). 수동 조회용 메모로 남은 것이라 삭제 또는 저장소 밖으로
옮기고 비밀번호를 변경해야 합니다. 사용자 계정이라 임의로 손대지 않았습니다.

**`.env` 5곳 → 루트 1곳** — `ECOS_API_KEY` · `ASOS_SERVICE_KEY` ·
`DATA_GO_KR_SERVICE_KEY` 는 아직 폴더별입니다. 코드는 이미 루트를 먼저 읽습니다.
