### P0 — 실제 운영 전 반드시 해결

1. **기상 수집기 완성**
  - 현재 `weather_asos_raw`가 2025-12-31에서 멈춰 있습니다.
  - 2026년 추론에서 학습에 사용한 기상 feature가 NULL이 될 수 있어 가장 큰 운영 블로커입니다.
2. **전체 배치 자동화**
  - 현재는 SQL 실행 순서와 수동 작업 의존성이 큽니다.
  - 수집 → 기준정보 갱신 → 학습 테이블 재생성 → 추론 → `prediction_log` 저장 → 실패 알림까지 하나의 재실행 가능한 배치로 묶어야 합니다.
3. **최신 데이터로 최종 검증**
  - 기상 데이터를 채운 뒤 `v5`를 재실행하고, `predict_input` 최신 기준일과 신선도 경고가 해소되는지 확인해야 합니다.
  - 자연키 정렬 수정 이후 테스트 성능도 다시 측정해야 합니다.
4. **모델 사용 가능 여부를 품목별로 제한**
  - 전체 평균은 좋아도 일부 조합은 baseline보다 나쁩니다.
  - `target_kind × item × lead time`별로 모델 사용/앵커 사용을 구분해야 합니다.

### P1 — 성능과 신뢰성 개선

5. **baseline을 확장**
  - 현재 “직전 영업일 가격 유지”는 적절한 1차 기준입니다.
  - 하지만 최근 7일 평균, 전년 동일시기, 계절 naive도 함께 비교해야 모델의 실제 개선 효과를 알 수 있습니다.
6. **평가 지표를 세분화**
  - 통합 WMAPE만 보지 말고 품목·타겟·리드타임별 WMAPE, MAE, 방향 정확도, baseline 대비 개선율을 고정 리포트로 관리해야 합니다.
  - 특히 마늘처럼 분모를 지배하는 품목 때문에 통합값이 왜곡될 수 있습니다.
7. **실제 사업 목표와 연결**
  - 현재 가격 예측 성능은 있지만, 저장비·감모율·마진·거래 주기가 모델 목표에 반영되어 있지 않습니다.
  - “몇 원 차이면 매입/매도 의사결정을 바꾸는가”를 정해야 모델 성능 목표도 정할 수 있습니다.
8. **예측 구간의 품질 검증**
  - `pred_lopred_hi`가 실제로 80%를 포함하는지 타겟·품목·리드타임별로 지속 측정해야 합니다.
  - 모델 내부 `seed_spread`와 실제 오차 구간을 혼동하지 않도록 운영 화면에서도 분리해야 합니다.
9. **학습/추론 코드 중복 제거**
  - 현재 `predict_input` 계산식이 학습 SQL 일부를 복제합니다.
  - 향후 두 코드가 갈라질 위험이 있으므로 feature 계산 로직을 공통 SQL 뷰·함수·생성 모듈로 통합하는 것이 좋습니다.

### P2 — 유지보수와 보안

10. **하드코딩 제거**
  - `tmp_holiday`, API 키·자격증명, 날짜 조건을 설정 파일이나 환경변수로 옮겨야 합니다.
  - 특히 문서에 언급된 자격증명 파일은 우선 폐기·교체하고 저장소 노출 여부도 확인해야 합니다.
11. **데이터 품질 모니터링 강화**
  - 수집 지연, 행 수 급감, 중복, 가격 단위 변화, 관측소명 불일치, 결측률 급증을 자동 감지해야 합니다.
  - 정상적인 결측과 사고성 결측을 구분하는 규칙도 코드화하는 편이 좋습니다.
12. **계약 문서 자동 검증**
  - DB 정의서·실제 스키마·모델 feature 목록·`prediction_log` 계약이 서로 일치하는지 CI나 배치 시작 단계에서 자동 검사하면 좋습니다.
13. **운영 이력과 재현성 관리**
  - 모델 버전, 학습 기간, feature 목록, seed, fixed iteration, 데이터 스냅샷을 예측 로그와 함께 남겨야 합니다.
  - 현재 문서의 “테스트 봉인”도 새 모델이 나올 때 자동으로 보존되게 만들 필요가 있습니다.

요약하면, 지금 가장 중요한 개선은 새 feature를 더 넣는 것이 아니라 **기상 수집 → 완전 자동 배치 → 품목별 안전한 모델 사용 정책 → 실제 사업 의사결정 연결**입니다.
