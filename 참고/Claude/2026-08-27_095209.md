# 2026-08-27 09:52:09

**Request:** was the DB column design itself wrong — why was auction price being
compared against a wholesale average?

**Short answer: the schema is not mislabelled, it is asymmetric. The three-target
migration was completed halfway, and a matching half-fix in `train.py` left the
mismatch behind.**

---

## 1. Nothing is joined incorrectly

`whsl_prc_avg7` is a correct 7-day wholesale average. `auc_prc_avg7` is a correct
7-day auction average. No column carries the wrong series.

What is wrong is which columns `train.py` *reads* when reporting baselines, and
which columns were never created at all.

## 2. The derived-column family is asymmetric

| Series | lag1 | lag3 | lag7 | avg7 | avg14 | std7 | prev_yr |
|---|---|---|---|---|---|---|---|
| **wholesale** | O | O | O | O | O | O | O |
| **auction** | O | O | · | O | · | · | · |
| **retail** | O | · | · | · | · | · | · |

Wholesale has the full family (7/7). Auction has 3/7. Retail has 1/7 — only its
anchor.

## 3. Why — the migration comment states its own faulty premise

`SQL/23_add_three_targets.sql` explains the design decision in its header:

> **▣ 왜 테이블을 나누지 않는가**
> **feature 28개가 완전히 동일하기 때문이다.** 학습은 타겟 컬럼만 바꿔 지정하면 된다.
> *(Why not split the table: because the 28 features are completely identical.
> Training only needs the target column swapped.)*

Acting on that premise, the migration adds exactly two columns —
`target_auc_prc` and `target_rtl_prc` — and nothing else.

**The premise is false under an anchor transform.** Each target has a paired anchor
(documented in `CLAUDE.md` §4), the anchor *is* the baseline by construction, and
therefore the baseline candidate set is target-specific too. Features are not
common across targets.

The project already had evidence against the premise and did not connect it: the
retail model runs on 24 features rather than 31, because ablation removed the seven
production-area weather columns for retail only. Feature sets had already diverged;
only the comment still carried the old assumption.

## 4. The precise omission

```
Stage 1  single-target project (wholesale)
         → whsl_prc_{lag1,lag3,lag7,avg7,avg14,std7,prev_yr} — full family
         → train.py hardcodes baseline candidates to whsl columns. Correct at the time.

Stage 2  three-target expansion (23_add_three_targets.sql)
         → adds two target columns only, on the "features are identical" premise
         → ANCHOR in train.py IS branched per target
         → the other two baseline candidates are NOT branched
```

**The anchor was made target-aware and its partner — the baseline set — was not.**
One half of a pair was fixed and the other was left behind.

## 5. This is not only a measurement problem

`whsl_prc_avg7` and `whsl_prc_std7` are **live features in every model**, including
the auction and retail models. So while predicting auction price, the model sees
wholesale volatility and has no auction volatility feature at all — `auc_prc_std7`
does not exist.

That reframes the finding. It looked like a reporting bug; it is also a **missing
feature** for two of the three targets.

## 6. Scope, revised

| # | Task | Note |
|---|---|---|
| 1 | **Add the missing derived columns in v5** — auction `lag7`/`avg14`/`std7`/`prev_yr`, retail `lag3`/`lag7`/`avg7`/`avg14`/`std7`/`prev_yr` | New. Requires a v5 edit and a full rebuild |
| 2 | Branch `train.py` baseline candidates per target | Small edit, restates recorded figures |
| 3 | Re-measure all three targets; decide on the α = 0.6 shrinkage anchor | Depends on 1 and 2 |
| 4 | Correct the `23_add_three_targets.sql` header and the column definition doc | The comment currently teaches the wrong premise |

No data needs recollecting. Both source tables (`auction_prices_daily`,
`veg_daily_price_raw`) already hold everything required; v5 only needs to run the
same window calculations it already runs for wholesale against the other two series.

Order matters: v5 edit → rebuild → re-measure.

## 7. What this does *not* affect

- **Training and predictions are unaffected.** The wholesale baseline columns were
  never used as labels. Nothing needs retraining because of the bug itself.
- **The recorded figures are not false, only weakly qualified.** `train.py` selects
  the lowest-WMAPE candidate; the mismatched columns always lost, so the anchor was
  always selected. "+5.4% for auction" is accurate as *"versus the anchor"*. What was
  wrong is calling it *"versus the strongest baseline"*.
- Wholesale is entirely unaffected — its baselines were correct throughout.

## 8. Why it still matters

Measured against a proper auction-series baseline, fold A (validation 2023) says a
plain 7-day moving average (0.1709) beats the current auction model (0.1767) by
3.4%. Until the baselines are target-correct we cannot answer the obvious challenge
— *"why not just use a moving average?"* — and today's shrinkage-anchor result
(α = 0.6 turns that into +2.5%) has no yardstick to be measured against.
